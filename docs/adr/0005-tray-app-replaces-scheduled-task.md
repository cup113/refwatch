# ADR-0005: 托盘常驻取代计划任务，CLI 保留为无头入口

Windows 上的默认形态从「计划任务每 30 分钟拉起一次 `pythonw watch.py`」改为
「托盘应用常驻，自己按 `interval_minutes` 跑轮次」。**引擎不动**：一轮的全部逻辑仍在
`watch.run_round()` 里，`main()` 只是把它翻成退出码，托盘与 CLI 共用同一份实现。

这条推翻了 README 里「no daemon」的定位，所以要记下为什么值：

- 用户要的是图形化的配置与编辑（#1），而「改配置」意味着改完要能立刻生效 —— 那需要一个
  活着的进程。计划任务是「跑完就死」，任何在它外面做的界面都只能改文件、等下一次运行。
- 计划任务把**调度**藏在注册表/任务计划程序里，工具自己的 `config.json` 里没有「多久跑一次」。
  托盘形态把 `interval_minutes` 收进配置，**调度**因此也变成可编辑、可备份、可解释的东西。
- 窗口问题没有因此变差：托盘进程本身就是 GUI 子系统，原规则（ADR-0003）原样适用。

## Considered Options

- **并存：托盘只管配置，调度仍归计划任务**：生命周期不变、改动最小，但「为什么要常驻一个
  什么都不干的进程」说不清，而且保存后仍要等下一次任务触发才生效。
- **彻底 GUI 化，删掉 `watch.py` 与 `install.ps1`**：会连带砍掉 Linux/cron、服务器、CI 冒烟、
  以及「零依赖脚本」这条退路 —— 而这些都是已经能用、且没有替代品的能力。
- **托盘常驻 + CLI 保留（采纳）**：多一个进程要管，但两个入口共享**一轮**的定义，
  `install.ps1` 与计划任务继续作为「不想常驻」的选择。

## Consequences

- 同一次安装里**同时**存在托盘与计划任务时，两套调度只会在 `.lock` 上互相跳过。所以托盘首次
  启动会检测同名计划任务并询问是否移除（`task_prompt_done` 记住已问过），绝不静默删除用户建的任务。
- `interval_minutes` 成为**调度**的唯一真相：`install.ps1 -Minutes` 也会写它，托盘面板改它。
- 无头路径仍然是第一等公民：`refwatch.exe --one-round`（或 `--dry-run`/`--no-notify`/`--repo`）
  直接走 `watch.main()`，计划任务与 `tools/window_probe.py` 都靠它。
- `watch.check_repo()` 不再管「要不要发送/要不要落盘」：dry-run 不推进基线由
  `run_round()` 的 save 门控负责。`tests/test_round_seam.py` 用真仓证明这条不变式。
